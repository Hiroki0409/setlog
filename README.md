# SetLog - 直近の記録を見ながら入力できる筋トレ記録アプリ

> 本READMEは企画・実装予定をまとめたものです。「実体験」「公開情報」「未検証の仮説」「実装予定」を区別して記載しています。

## 1. サービス概要

SetLogは、種目ごとの直近の記録を同じ画面で確認しながら、今回の重量・回数・セット数を入力できるWebアプリです。  
主な対象は、重量・回数を使った筋トレの記録と振り返りを行いたい人です。  
記録・確認に機能を絞った構成が役立つかを、最小限のMVPで検証します。

「過去の記録を探すのに苦労した」「多機能で使いづらかった」「記録が面倒で続かなかった」といった経験は、私の実体験としては確認できていません。

### 2-2. なぜそれが「気になった」のか

既存アプリを使って記録していた経験から、卒業制作で扱う範囲を「種目ごとの記録を残すこと」と「保存した数値を確認すること」に絞りました。

そのうえで、**直近の記録と今回の入力欄を同じ画面に置く構成が、利用者にとって分かりやすいか**を検証する方針です。これは開発上の着眼点であり、私自身が既存アプリの操作に不満を感じていたという意味ではありません。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

**確認済みの事実：私自身は「筋トレメモ」の利用に特に不便を感じていませんでした。** 解決すべき具体的な不便を裏付ける、利用者への聞き取り結果も未確認です。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

最初の検証対象として、次の人物像を仮置きします。

- 年齢・属性：仕事と両立しながらジムで筋トレを行う30代の社会人。
- 運動習慣：週2〜4回程度、重量・回数で記録する種目に取り組む人。
- 利用場面：スマートフォンを使い、セットの合間やトレーニング後に記録する人。
- 利用目的：種目ごとの重量・回数・セット数を残し、過去の数値を確認することを主な用途とする人。

年齢や頻度は、試用場面を具体化するための**仮の条件**です。開発者本人の年齢・頻度を示すものではなく、この層に特有の課題や需要があることも未確認です。聞き取りで属性より記録する場面・参照する情報が重要だと分かれば、対象の定義を調整します。

### 4-2. 自分とユーザーの距離

筋トレ記録アプリを利用したことがあるという点では、**自分自身に近いユーザー**を想定しています。開発したアプリは、まず自分で記録・確認の流れを試します。

一方で、私は既存アプリに特に不便を感じていなかったため、「操作に困っているユーザー」の代表ではありません。自分の試用で操作できたことと、他の人に需要があることは分けて判断します。

### 4-3. 実際に使われる可能性について（需要・存在確認）

筋トレ記録アプリを利用している自分がいることと、第5章の既存サービスが提供されていることから、筋トレを記録する用途があることは確認できます。ただし、**SetLogを新たに利用する需要や、既存サービスから乗り換える理由は未確認**です。

検証は次の順で行う予定です。

1. 自分で少なくとも2回の記録を行い、初回入力と、保存済み記録を参照した次の入力を試す。
2. 可能であれば、筋トレを行う知人1〜2名に協力を依頼する。協力者の確保は今後の確認事項とする。
3. 現在の記録方法と不満の有無を先に聞き、その後に種目の登録・記録・再入力を試してもらう。不満があることを前提に質問しない。
4. 操作で迷った点、直近の数値を実際に参照したか、再び使いたいか、その理由を確認する。

操作が完了できるかと、使い続けたい理由があるかを別々に確認します。少人数の試用結果を一般的な需要の証明とは扱いません。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ（導入・継続の流れ）

初期は開発者自身の利用と、協力者への試用依頼を入口とします。一般利用者が自然に集まることは前提にしていません。

1. サービス紹介で「種目別の直近の記録を見ながら入力できる」ことを確認し、試用する。
2. アカウントを作成してログインする。
3. 使用する種目を名前だけで登録する。
4. 種目の新規記録画面で、実施日・重量・回数・セット数を入力して保存する。
5. 次に同じ種目の新規記録画面を開くと、直近の記録が入力欄と同じ画面に表示される。必要に応じて参照し、今回の記録を保存する。
6. 履歴を見返し、誤りがあれば編集・削除する。

登録する理由はこの使い方を試すこと、継続する理由の仮説は自分の記録が蓄積し、次の入力時に参照できることです。実際に登録・継続の理由になるかを試用で確認します。

## 7. このアプリで実現すること

### MVPで作る機能

| 機能 | 実装する範囲 |
| --- | --- |
| ユーザー認証 | ユーザー登録・ログイン・ログアウト |
| 種目の管理 | 自分が使用する種目の名前を登録・一覧表示 |
| トレーニング記録 | 種目・実施日・重量（kg）・回数・セット数を保存 |
| 直近の記録の表示 | 選んだ種目の新規記録画面に、保存済みの記録1件を表示 |
| 履歴の管理 | 自分の記録の一覧表示・編集・削除 |
| データの分離 | 表示・登録・編集・削除のすべてで、本人の種目・記録だけを扱う |
| スマートフォン対応 | 入力欄・数値・保存ボタンを見やすく配置 |

**記録の単位**

1件の記録を「同じ重量・同じ回数で実施した1セット以上」とします。例えば、60kg・10回・3セットを1件として保存します。重量や回数が異なる場合は、別の記録として入力します。

MVPの対象は重量・回数・セット数で表せる筋トレです。時間・距離による記録や、複数セットをそれぞれ異なる内容で一括入力する機能は含めません。

**「直近の記録」の定義**

- ログインユーザー本人の、選択した種目の保存済み記録を対象とする。
- 実施日が最も新しい1件を表示する。同じ実施日の記録が複数ある場合は、後から作成した記録を表示する。
- 実施日・重量・回数・セット数を表示する。該当する記録がなければ「まだ記録がありません」と表示する。
- 同日中に保存した記録も対象とする。前回のトレーニング全体を表示する機能ではない。
- 過去の日付の記録を入力するときも、保存済み記録全体で実施日が最新の1件を表示する。入力中の日付に応じた検索や、自動入力・コピーは行わない。

種目一覧から対象の種目を選んで新規記録画面を開く構成とし、画面内で種目を切り替えるための複雑な処理は設けません。

**MVPの完了・検証条件**

公開環境で「登録・ログイン → 種目登録 → 記録保存 → 次の入力時に直近記録を確認 → 編集・削除」の一連の操作ができ、別のユーザーのデータにアクセスできないことを確認します。そのうえで第4章の試用を行い、操作性と再利用したい理由を確認します。

### 本リリースで作る機能

現時点で追加機能は確定していません。MVPの試用で見つかった入力・表示の問題を修正し、基本機能の安定性を高めることを優先します。

グラフ、お気に入り、CSVエクスポートは、必要性が確認できた場合に検討する候補です。本リリースの必須機能としては約束せず、MVPの完成条件にも含めません。SNS、AI、通知、外部サービス連携は今回の開発範囲に含めません。

Railsは、公開時点でセキュリティ修正の対象となるバージョンを採用します。[Rails公式メンテナンスポリシー](https://rubyonrails.org/maintenance)を確認し、具体的なバージョンは環境構築時に記録します。

主なデータは、User（ユーザー）、Exercise（種目）、WorkoutRecord（トレーニング記録）の3モデルで管理する予定です。ユーザーが種目を持ち、その種目に記録を紐づけます。

### 10-2. 技術選定の比較検討

| 技術・構成 | 方針 | 理由 |
| --- | --- | --- |
| Ruby on RailsとERB | 採用予定 | 学習内容を活用し、画面表示とデータ保存を一つのアプリで扱うため |
| ReactとAPIの分離構成 | 今回は不採用 | 今回の画面と入力処理を実現するうえで、別構成の導入を必要としていないため |
| MySQL | 採用予定 | 学習で使用した経験を活用するため |
| PostgreSQL | 現時点では不採用 | MySQLを優先する。ただし公開環境の制約があれば比較し直す |
| Devise | 採用予定 | Rails向けの既存認証ライブラリを利用するため。導入後もデータの所有者確認は別に実装する |
| 追加のUIフレームワーク | 今回は不採用 | 必要な画面をERBとCSSで構築し、導入する技術を絞るため |

取り組む点は、本人の種目と記録だけを取得し、直近の記録を新規入力画面に表示する処理です。認証ライブラリの機能は[Devise公式README](https://github.com/heartcombo/devise)を参照します。

### 10-3. キャッチアップ不足の懸念

- **認証とデータの分離：** ログイン済みかどうかだけでなく、指定された種目・記録が本人のものかを、各処理で確認する必要があります。
- **直近の記録の取得：** 本人・選択種目で絞り、実施日の降順、同日なら作成順の降順で1件取得します。記録なし・同日複数・過去日の追加・編集後の表示を確認します。
- **入力チェック：** 実施日・種目の必須入力、重量が0以上の数値であること、回数とセット数が1以上の整数であることを確認します。
- **バージョンと公開環境：** Rails・Ruby・Deviseの互換性と、MySQLの接続・データ保持・費用を確認します。デプロイ先は未決定のため、選定と接続確認を初期作業に含めます。

新しい技術を増やすことよりも、MVPを公開し、記録・確認の流れを検証できる状態にすることを優先します。
