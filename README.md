# SetLog - 前回の実施日の記録を見ながら入力できる筋トレ記録アプリ

> 本READMEは企画・実装予定をまとめたものです。「実体験」「公開情報」「未検証の仮説」「実装予定」を区別して記載しています。

## 1. サービス概要

SetLogは、同じ種目の前回の実施日に保存した全記録を見ながら、今回の重量・回数・セット数を入力するWebアプリです。  
主な対象は、仕事と両立しながら週2〜4回程度ジムで筋トレを行う30代の社会人のうち、筋トレ記録アプリを利用し、セットごとに重量・回数を変えながら前回の内容を参考にしたい人です。  
前回の複数の記録を入力画面で参照できることが、履歴を探し直す手間の軽減につながるかを検証します。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

**本人の実体験として確認できていること**

- 筋トレの記録に「筋トレメモ」というアプリを利用している。
- 直近の記録は常に表示されている。それより過去の記録を見るには「MORE」を押して確認する。
- 参考にしたいのは、今日の直前のセットではなく、前回のトレーニングの重量・回数である。
- ウォームアップでは軽い重量を使い、本番では重くする。また、セットごとに重量や回数を調整する。
- 既存アプリに特に不便とは感じていなかった。

「MOREを押すのが面倒だった」「今日の記録を保存すると前回の表示が消えて困った」という経験は確認できていません。MOREを押す前後の詳細な画面遷移や、現在のアプリで前回の複数セットがどこまで表示されるかも、まだ整理できていません。

卒業制作では、利用経験のある題材で、記録を保存して振り返る基本的なWebアプリを完成させることを目指しています。既存アプリへの不満を開発動機として作ることはせず、実際に参考にしたい情報から企画を具体化します。

### 2-2. なぜそれが「気になった」のか

前回の内容を参考にしたい一方、同じ種目の中でも重量や回数を変えているため、保存済みの最新1件だけでは必要な情報を表せないと考えました。

例えば、今日40kgのウォームアップを保存した後も、参考にしたいのは前回の60kgや、後半に回数を減らしたセットです。この例は仕様を考えるための架空の数値であり、本人の実際の重量ではありません。

そこで、入力対象の日付より前の、同じ種目の最新の実施日を選び、その日に保存した全記録を入力欄と同じ画面に表示する方針とします。この構成が現在の方法より役立つかは未検証です。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

本人が既存アプリで感じている具体的な不便は、現時点では確認できていません。ただし、「前回の内容を参考にしたい」「セットごとに内容を変える」という利用場面は確認できました。

改善対象として検証するのは、**今回の重量・回数を考えるときに、前回のウォームアップや本番の複数の記録を探し直す手間**です。

この手間が発生するという考えは仮説です。根拠は、参照したい情報が複数の記録に分かれる本人の記録方法と、最新1件だけを表示する従来のSetLog案ではそれを満たせないことです。既存アプリで同じ手間が実際に発生していると確認したわけではありません。

### 3-2. 本当に解決したい課題は何か

| 問い | 整理した内容 | 根拠・確認状況 |
| --- | --- | --- |
| なぜ前回の内容を確認するのか | 今回の重量や回数を決める参考にしたいため | 本人の回答で確認済み |
| なぜ最新1件では足りないのか | ウォームアップと本番で重量が異なり、セット間でも内容を調整するため、1件が前回全体を代表しない | 記録方法は実体験。必要な表示範囲は試用で確認する設計判断 |
| なぜ前回の全記録を入力画面にまとめるのか | 必要な数値が同じ画面にあれば、別の履歴を探し直す操作を省ける可能性があるため | 未検証の仮説。現在の方法でその操作が必要か、負担かを比較する |

**MVPで検証する仮説（一文）**

筋トレ記録アプリを利用し、セットごとに重量・回数を変えながら前回の内容を参考にする人は、同じ種目の前回の実施日の全記録を今回の入力画面で参照できることで、必要な過去の数値を履歴から探し直す手間を減らせるのではないか。

現在の方法ですでに必要な情報を確認でき、手間にも差がなければ、この仮説は支持されなかったと判断します。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

想定するターゲットは、次の属性・運動習慣と記録方法を持つ人です。

- 年齢・属性：仕事と両立しながらジムで筋トレを行う30代の社会人。
- 運動習慣：週2〜4回程度、重量・回数で記録する種目に取り組む人。
- 現在の記録方法：既存の筋トレ記録アプリを使い、種目ごとの記録を残している人。
- 筋トレの方法：ウォームアップと本番で重量を変え、セット間でも重量や回数を調整する人。
- 参照目的：前回のトレーニング内容を参考に、今回の重量や回数を決めたい人。
- 検証する場面：今日の記録を追加しながら、前回の同じ種目の複数の記録を見返す場面。

年齢・属性・運動頻度は、対象者を具体的に示すための仮のターゲット設定です。開発者本人の確認済み属性や、この層に需要があると確認した結果ではありません。記録方法・参照目的と組み合わせて、利用価値を検証します。

最初の試用者は開発者本人です。本人は「筋トレメモ」を利用し、常に表示される直近の記録を確認し、それより過去の記録はMOREを押して確認しています。この操作は本人の利用経験であり、想定ユーザー全員が同じ手順を取ると確認したわけではありません。

### 4-2. 自分とユーザーの距離

想定ユーザーと自分自身の共通点は、筋トレ記録アプリを利用し、セットごとに重量・回数を変えながら、前回の内容を参考にすることです。まずはこの共通する利用場面を自分で試し、必要な情報を確認できるかを検証します。本人の試用結果だけで、想定する年齢・属性・運動頻度の人にも価値があるとは判断しません。

一方、既存アプリには特に不便を感じていません。自分が試す理由は卒業制作の検証であり、既存アプリから乗り換えたいという意思が確認できたわけではありません。

### 4-3. 実際に使われる可能性について（需要・存在確認）

記録と前回の参照という用途は本人の経験から確認できていますが、SetLogを新たに選ぶ需要は未検証です。

1. まず現在のアプリで、前回のウォームアップ・本番・回数を調整した記録を確認する手順を整理する。今日の記録を追加した後も前回を参照できるか、MOREが必要なのはどの情報かを確認する。
2. 本人の試用では、同じ種目について少なくとも別の2日分を記録する。1日目に異なる重量・回数を登録し、2日目にそれらを参考に入力する。
3. 今日のウォームアップを保存した後も、前回の必要な情報が表示され続けるかを確認する。
4. 現在の方法と同じ記録例で比較し、必要な数値を確認できたか、履歴を探し直す操作が必要だったか、どこが役立ったか・役立たなかったかを記録する。
5. 可能であれば、同様の記録方法・参照目的を持つ知人1〜2名にも試用を依頼する。協力者の確保は今後の確認事項とする。

操作できたかに加えて、必要な情報が足りたか、現在の方法に対して利用理由があるかを別々に判断します。違いを感じなければ、その結果も残します。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ（導入・継続の流れ）

初期は本人の試用と協力者への依頼を入口とします。

1. アカウントを作成してログインし、使用する種目を名前だけで登録する。
2. 種目と実施日を選び、記録画面を開く。実施日は当日を初期値とする。
3. 初回は参照できる過去の記録がないため、今回の重量・回数・セット数を保存する。内容が変われば別の記録として追加する。
4. 次の実施日に同じ種目を選ぶと、前回の実施日の全記録が入力画面に表示される。
5. 前回の内容を参考に今回の内容を決め、入力する。今日の記録を追加しても、参照する前回の日付は変わらない。
6. 必要に応じて記録一覧から編集・削除する。

登録の入口は試用依頼です。継続理由として検証するのは、蓄積した前回の情報が必要な形で見え、現在の方法より確認・入力に役立つかどうかです。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

**実装で提供する予定の体験**

同じ種目の前回の実施日に保存した全記録を、今回の入力欄と同じ画面に表示します。今日のウォームアップや本番の記録を追加しても、前回の表示対象は変えません。

**検証する変化**

- 行動：前回の必要な重量・回数を、履歴を探し直さず確認できるか。
- 気持ち：必要な情報がそろい、確認から入力まで迷わず進めると感じるか。
- 考え方：現在の方法と比較して、次のトレーニングでも利用したい理由があるか。

入力時間の短縮や継続率の向上といった効果は未検証です。

### 6-2. 価値を一文で表す

SetLogは、セットごとに重量・回数を変える筋トレ実践者が、同じ種目の前回の実施日の全記録を参照しながら、今回の内容を決めて記録できるようにするサービスです。

「その表示によって履歴を探し直す手間を減らせるか」を、第3章の仮説として検証します。

## 7. このアプリで実現すること

### MVPで作る機能

| 機能 | 実装する範囲 |
| --- | --- |
| ユーザー認証 | ユーザー登録・ログイン・ログアウト |
| 種目の管理 | 自分が使う種目の名前を登録・一覧表示 |
| トレーニング記録 | 種目・実施日・重量（kg）・回数・セット数を保存 |
| 前回の実施日の表示 | 選択した種目・実施日を基準に、前回の実施日の全記録を新規入力画面に表示 |
| 履歴の管理 | 自分の記録の一覧表示・編集・削除 |
| データの分離 | 本人の種目・記録だけを表示・登録・編集・削除できること |
| スマートフォン対応 | 前回の数値・入力欄・保存ボタンを見やすく配置 |

**記録の単位**

1件は「同じ種目・実施日で、連続して同じ重量・同じ回数で実施した1セット以上」とします。例えば60kg・10回・2セットを1件にまとめ、次が60kg・8回なら別の1件にします。すべてを1セットずつ記録することも可能です。

重量・回数・セット数の項目を維持し、異なる内容は別の記録として保存します。複数行の一括入力、ウォームアップの専用区分、自動コピー、時間・距離の記録はMVPに含めません。

**「前回の実施日」の定義**

- 本人の、選択した種目の記録だけを対象とする。
- 入力対象の実施日をDとし、Dより前で、その種目の記録がある最も新しい日付を「前回の実施日」とする。前日とは限らない。
- その日に保存した全記録を、作成順に表示する。表示項目は実施日・重量・回数・セット数。最後の1件だけを抜き出さない。
- D当日とDより後の記録は参照対象に含めない。今日の記録を何件追加しても、前回の表示は今日の記録に置き換わらない。
- 過去日の追加入力でも、入力対象日Dを基準に前回を求める。
- 該当する日がなければ「この実施日より前の記録はありません」と表示し、通常どおり入力・保存できるようにする。
- 種目・実施日を確定して入力画面を開く。日付を変更する場合は再表示して参照対象も更新する。非同期更新は必須としない。
- MVPでは同じ種目・同じ日付を一つの実施単位とし、同日の朝・夜などを別セッションとして分けない。全記録とは、その種目・実施日の保存済み記録を指し、未入力のセットは含まれない。

**具体的な記録例（仕様説明用の架空の数値）**

| 実施日 | 種目 | 重量 | 回数 | セット数 |
| --- | --- | --- | --- | --- |
| 11月9日 | ベンチプレス | 40kg | 10回 | 1セット |
| 11月9日 | ベンチプレス | 60kg | 10回 | 2セット |
| 11月9日 | ベンチプレス | 60kg | 8回 | 1セット |
| 11月12日 | ベンチプレス | 40kg | 10回 | 1セット |

11月12日の入力画面では、11月9日の3件をすべて表示します。11月12日の40kgを保存した後も表示対象は変わりません。本人は前回の60kg・10回だけでなく、最後の8回も参考にできます。アプリが次の重量や回数を推奨・自動決定する機能は設けません。

**MVPの完了・検証条件**

公開環境で認証・種目登録・記録保存・前回表示・編集・削除ができ、他人のデータにアクセスできないことを確認します。上記例に加え、過去日入力・前回なし・他種目の混在でも定義どおり表示できることを確認します。

その後、第4章の試用で「必要な情報を確認できたか」「現在の方法よりどの操作が減ったか」「役立った点・役立たなかった点」を確認します。操作できたことだけで価値を検証できたとは扱いません。

## 8. このアプリの懸念点とその対策

### 懸念点

以下は、企画・設計上の懸念です。本人が既存アプリで経験した不便を示すものではありません。

| 懸念点 | なぜそう考えるか | 対策 |
| --- | --- | --- |
| SetLogを選ぶ理由がない可能性 | 本人は既存アプリに特に不便を感じておらず、類似機能も既に存在する | 現在の記録方法と利用理由を聞き、課題・需要がなければ対象や企画を見直す |
| 初回の種目登録が手間になる可能性 | 記録開始前に種目を準備する必要がある | 種目名だけで登録できるようにし、初回の流れを試用で確認する |
| セットごとに内容が異なると入力が増える | 同じ重量・回数のセットをまとめて記録する方式のため | 入力ルールを画面に明記し、異なる内容は別の記録として保存する。負担の程度を試用で確認する |
| 前回の全記録でも必要な情報が不足する可能性 | 未入力のセットや、同日の別セッションは判別できないため | 保存済みの全記録を表示する仕様を明記し、本人の試用で情報が足りるか確認する |
| 初回は参照できる記録がない | まだデータが保存されていないため | 「この実施日より前の記録はありません」と表示し、そのまま入力・保存できるようにする |
| スマートフォンで入力しづらい可能性 | 数値入力と画面の確認が中心となるため | 数値用の入力欄と見やすいボタンを用意し、実機で確認する |
| 他人のデータを参照・変更できてしまう可能性 | ユーザーごとにデータを保存するため | 認証に加え、サーバー側で所有者を確認する。別ユーザーによる参照・更新・削除を拒否できることをテストする |
| 開発・公開に時間がかかる可能性 | 機能追加や公開環境の選定が後になると作業が増えるため | 初期に公開環境を確定して接続を試し、MVPの機能を優先する |

| 候補 | 検討する条件 |

| 入力欄・説明・画面配置の改善 | 試用で入力ミスや迷う箇所が見つかった場合 |
| お気に入りやよく使う種目の表示 | 種目が増え、選択に手間がかかることが確認できた場合 |
| 記録の推移グラフ | 一覧だけでは変化を把握しづらいという要望が確認できた場合 |
| CSVエクスポート | 利用者が記録を手元に保存・活用したいと希望した場合 |
| 使い方の説明の改善 | 記録単位などの説明を改善することで、迷いを減らせる場合 |

これらは発展候補であり、実装を約束するものではありません。利用価値が確認できない場合は、追加機能で補おうとせず、課題と対象ユーザーを再検討します。

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

| 区分 | 採用予定 |
| --- | --- |
| 言語 | Ruby、HTML、CSS。JavaScriptは必要な箇所のみ |
| フレームワーク | Ruby on Rails。使用バージョンは保守状況とライブラリの互換性を確認して確定 |
| 画面 | ERBとCSS |
| データベース | MySQL |
| 認証 | Devise |
| テスト | RSpec。基本操作・入力チェック・データの所有者確認を重点的に検証 |
| 開発・管理 | Git、GitHub |
| デプロイ先 | 未決定。RailsとMySQLの利用条件・費用・学習済みの手順を確認し、実装初期に確定 |

Railsは、公開時点でセキュリティ修正の対象となるバージョンを採用します。[Rails公式メンテナンスポリシー](https://rubyonrails.org/maintenance)を確認し、具体的なバージョンは環境構築時に記録します。

主なデータは、User（ユーザー）、Exercise（種目）、WorkoutRecord（トレーニング記録）の3モデルで管理する予定です。ユーザーが種目を持ち、その種目に実施日付きの記録を紐づけます。前回表示は実施日でまとめて取得し、MVPではセッション用モデルを追加しません。

### 10-2. 技術選定の比較検討

| 技術・構成 | 方針 | 理由 |
| --- | --- | --- |
| Ruby on RailsとERB | 採用予定 | 学習内容を活用し、画面表示とデータ保存を一つのアプリで扱うため |
| ReactとAPIの分離構成 | 今回は不採用 | 今回の画面と入力処理を実現するうえで、別構成の導入を必要としていないため |
| MySQL | 採用予定 | 学習で使用した経験を活用するため |
| PostgreSQL | 現時点では不採用 | MySQLを優先する。ただし公開環境の制約があれば比較し直す |
| Devise | 採用予定 | Rails向けの既存認証ライブラリを利用するため。導入後もデータの所有者確認は別に実装する |
| 追加のUIフレームワーク | 今回は不採用 | 必要な画面をERBとCSSで構築し、導入する技術を絞るため |

取り組む点は、本人の種目と記録だけを取得し、前回の実施日の全記録を新規入力画面に表示する処理です。認証ライブラリの機能は[Devise公式README](https://github.com/heartcombo/devise)を参照します。

### 10-3. キャッチアップ不足の懸念

- **認証とデータの分離：** ログイン済みかどうかだけでなく、指定された種目・記録が本人のものかを、各処理で確認する必要があります。
- **前回の記録の取得：** 本人・選択種目で絞り、入力対象日より前の最大の実施日を求め、その日の全記録を作成順に取得します。当日の記録を除外できること、過去日入力・前回なし・同日複数・他種目・他ユーザー・編集や削除後の再表示を確認します。
- **入力チェック：** 実施日・種目の必須入力、重量が0以上の数値であること、回数とセット数が1以上の整数であることを確認します。
- **バージョンと公開環境：** Rails・Ruby・Deviseの互換性と、MySQLの接続・データ保持・費用を確認します。デプロイ先は未決定のため、選定と接続確認を初期作業に含めます。

新しい技術を増やすことよりも、MVPを公開し、記録・確認の流れを検証できる状態にすることを優先します。
